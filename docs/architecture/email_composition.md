# Email composition

The backend renders its emails from templates in this repository, on one shared layout,
and hands each one to the [email outbox](email_outbox.md) as a provider-neutral
`OutgoingEmail` (from, reply-to, to, subject, HTML, plain text, attachments). Senders move
here from Resend-hosted templates one at a time; see [Email notifications](email_notifications.md)
for which have moved.

## Stack

| Piece | Why |
|---|---|
| [askama](https://askama.rs/) | Compile-time Jinja templates. Each email is a typed struct, so a template that names a field the struct lacks fails the build. `.html` escapes by default; `.txt` does not. `{% extends %}` gives every email one layout. |
| [css-inline](https://crates.io/crates/css-inline) (`default-features = false`) | The layout keeps one `<style>` block; it is inlined onto each element at render for Gmail and Outlook. `@media` rules (dark mode, narrow screens) cannot be inlined and are kept in a `<style>` tag. One static inliner, with remote stylesheets off. |
| [insta](https://insta.rs/) (tests only) | Snapshots of each email's copy, reviewed in pull requests as the contract for what it says. |

Not adopted: MJML (a second syntax parsed at runtime), runtime template engines (errors
surface only when an email is sent), and generating the plain text from the HTML (its
output is not clean enough to send).

## Shape

```
domain/templates/email/
  base.html  base.txt        the layout: logo, card with title and greeting, content, footer
  macros.html                the details block and its rows, the notice, Now/Before, the button
  <kind>.html  <kind>.txt    one pair per email
domain/src/email_composition/
  mod.rs       Email, compose, Brand, Person, When, Parties, Actor, templates!
  session.rs   SessionScheduled, SessionRescheduled, SessionCancelled, SessionReminder
  series.rs    SeriesScheduled, SeriesRescheduled, SeriesCancelled
```

Each email is a struct of facts already formatted for its recipient: dates in their zone,
the session label from the relationship's kind, the other participant. Templates only lay
those facts out. A fact that is sometimes absent is an `Option` (a previous time, a session
title); one that changes the copy is an enum (`CancelReason`, `Scope`, `Actor`), matched in
the template.

```rust
pub trait Email: Bodies {
    const KIND: &'static str;          // the outbox `kind`
    fn recipient(&self) -> &Person;    // the `to:` address
    fn subject(&self) -> String;
    fn attachments(&self) -> Vec<Attachment> { Vec::new() }
}

pub fn compose<E: Email>(email: &E, brand: &Brand) -> Result<OutgoingEmail, Error>;
```

`Bodies` (the HTML and text renders) is generated by `templates!`, which emits the two
askama wrappers for an email from its pair of template paths; the derive needs literal
paths, so each email names its own. The subject is built in Rust; the preheader is a
`{% block preheader %}` in the email's HTML template.

`Brand` holds what every email shares: the `From:` (`Refactor Coach
<hello@mail.myrefactor.com>`), the reply-to and support address (`hello@refactorcoach.com`),
and the links under `FRONTEND_BASE_URL`: the logo (`/22JHC_Monogram_RGB_small.png`, a
frontend public asset) and the privacy policy (`/privacy`). It needs no environment
variable of its own; without `FRONTEND_BASE_URL` composed emails are skipped and logged.

## Layout

Hand-written for email clients: nested tables with `role="presentation"`, a 600px
`<!--[if mso]>` wrapper for Outlook, `<html lang="en">`, a `<title>`, a hidden preheader
padded so clients don't pull body text into the inbox preview, and `color-scheme`
metadata. The plain-text part is written by hand per email, with each link as a bare URL
on its own line.

It follows refactor-platform-fe's `docs/design-system.md`, and its email spec (section 14)
in particular: a Well canvas behind one white card (1px border, 16px radius, 32px
padding), Inter where it is installed and the system stack elsewhere (no web font is
loaded), and the spec's type scale. Inside the card come a short sentence-case title,
"Hi {first name},", one or two sentences, a details block of label-over-value rows (When,
With, Length, and Where when there is a meeting link), one pill button labelled as the
app labels it ("Open session"), and a secondary line naming the calendar attachment.
Cancellations put their statement in a neutral notice and have no button. The footer
below the card says why the person received the email, with the organization's name,
plus the contact address and the company and privacy links.

Two deliberate departures from section 14: the R monogram logo sits above the card in
place of the text wordmark, and a reschedule shows the **Now** panel on the brand tint
first, then a quiet **Before** with only what changed (the spec puts "Was" first). The
other person is always named in full. The plain text follows the same structure: the
title, `Label: value` lines, `Now:` and `Before:` headings, and the footer.

The colors are the frontend's tokens in hex, light and dark, and appear only in
`base.html`'s stylesheet; templates and macros use its classes. A token change in the
design system should be mirrored there.

## How a sender moves

1. Build the email's struct per recipient with the existing helpers in `emails.rs`
   (`Participants::copies`, and `session_when` for a start in the recipient's zone).
2. `compose` it with the `Brand`, and wrap it in an `Envelope` with its kind,
   `Subject::CoachingRelationship(id)` (or `Subject::User`) and recipient.
3. Load what the emails name before the transaction begins: a failed read inside it would
   abort it in Postgres, so its commit would roll the change back while the call reported
   success. Inside the transaction, only render (no reads) and `email_outbox::enqueue`.
   A load or render failure is logged and costs only the email; only the outbox write can
   fail the transaction.
4. Remove the sender's Resend template path and its `*_TEMPLATE_ID` from the config and
   every passthrough layer.

The single-session emails follow this through one `SessionNotice`, which loads the brand,
the parties, who may be reached and the invite's zone before the transaction, then renders
and writes each reachable participant's email inside it. An invite's `.ics` DESCRIPTION
lists the topics, goals and actions of an `Agenda` given when it is written:

- **Cancelled**: the session delete writes both participants' emails in its transaction.
- **Scheduled**: the session create writes both members' emails last in its transaction,
  after the hydration tasks. Its DESCRIPTION lists the goals and topics those tasks
  returned, so the invite names exactly what the create commits.
- **Rescheduled**: the pending reschedule sweep writes each member's email of the session
  as its transaction locked it, restamps their notice and settles the row together. It names
  the start they last heard of only when the start moved. Without `FRONTEND_BASE_URL` the
  row is settled unsent.
- **Owed invites**: the pending reschedule sweep writes one participant's scheduled email
  in a transaction that bumps the session's `SEQUENCE` and settles the owed row. Without
  `FRONTEND_BASE_URL` the row is settled unsent.
- **Series cancelled**: the series delete writes both participants' emails in its
  transaction, after its session locks and the series row, carrying the series `CANCEL` at
  its bumped `SEQUENCE` and a `CANCEL` for each legacy member's standalone event. Its dates
  are each upcoming session's own start in the recipient's zone. A `SeriesNotice` loads what
  they name before the transaction, as `SessionNotice` does.
- **Resent invites**: `POST /coaching_sessions/{id}/resend_invite` renders the same email
  and hands it to the `Mailer` at once, so it can still answer whether it was delivered.
  With no email provider it answers 502 without bumping `SEQUENCE`.
Production refuses to start without `FRONTEND_BASE_URL`, next to the email provider check. The standalone-event cancellations that series edits owe
still follow the series scheduled and rescheduled emails, which send after their own
transaction, so they are enqueued in a transaction of their own right after it until those
emails move.

## Tests

- `email_composition/session_tests.rs`, `series_tests.rs`: one snapshot of the subject,
  preheader and text per email and per branch that changes its copy, plus a test per
  optional fact shown both ways.
- `email_composition/tests.rs`: one HTML snapshot (the session-scheduled email) as the
  layout's contract; escaping of user text; every HTML link present in the text; what
  `compose` addresses and attaches; the inlined stylesheet keeping its `@media` rules.
- CI runs with `INSTA_UPDATE=no`, so a changed email fails until its snapshot is reviewed
  and accepted (`cargo insta review`, or rerun with `INSTA_UPDATE=always` and read the diff).
- To look at the emails in a browser, run
  `EMAIL_PREVIEW=https://app.myrefactor.com cargo test -p domain write_previews -- --ignored`;
  each kind is written to `target/email-preview/<kind>.html`.
